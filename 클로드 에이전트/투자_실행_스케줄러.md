## 설계의 중심 — 실행과 조회의 분리

유저는 결과를 **읽기만** 하므로, 매매 로직이 Streamlit 앱 프로세스 안에 살 이유가 없다.
분리하면 오히려 세 가지가 동시에 해결된다:

- 여러 방문자가 우연히 겹쳐 매매를 중복 실행할 위험이 **원천적으로 사라진다**.
- Streamlit 쪽에 쓰기 권한 토큰을 둘 필요가 없어진다 (GitHub Actions만 커밋한다).
- (V1은 규칙 기반이라 해당 없음, LLM 전환 시엔) `ANTHROPIC_API_KEY`도 Streamlit Cloud가 아니라 GitHub Actions Secrets에만 두면 된다.

> 초기 설계에는 "누군가 대시보드를 열면 그날 매매를 실행"하는 방식이 있었으나, 사용자가
> "프로그램이 자동으로 돌고 나는 읽기만 한다"고 요구사항을 명확히 하면서 폐기했다.

## KRX 스냅샷 갱신 시각 — 실측 완료 (구현 0순위였음)

`screener.py`는 KRX를 직접 치지 않고 FinanceDataReader의 **GitHub 미러**에서 그날 스냅샷을
가져오는데, 이 미러가 몇 시에 갱신되는지는 우리가 통제할 수도 보장받을 수도 없는 제3자 사정이라
**추정하지 않고 GitHub 커밋 이력을 직접 조회해 확인했다.**

결과: 최근 완료된 거래일 4일 모두 파일의 **최종(확정) 커밋이 18:15~18:49 KST 사이**에 왔다
(그 전엔 새벽부터 하루 6~7번 중간 갱신이 있다 — 스텁 상태로 오해하지 말 것). 처음 가정했던
"17:00 KST"는 **틀렸다** — 그 시각엔 아직 전날 데이터였다. 그래서 cron은 **19:30 KST**로
확정했다(관측 구간보다 40분~1시간 15분 여유). 상세 표는 PRD 5.5.

표본이 4일뿐이므로, 스크립트는 여전히 **오늘 스냅샷이 없으면 에러 없이 조용히 종료**하게 짠다.
이렇게 하면 평일 공휴일(설·추석)도 자동으로 처리되고, 어쩌다 더 늦게 확정되는 날에도 앱이
죽지 않는다. 배포 후 첫 2~3주는 19:30 KST에 실제로 그날 데이터가 잡히는지 계속 관찰한다.

## 지켜야 할 것

- **실패 시 원장을 건드리지 않는다.** 시세 조회 실패 등으로 중간에 죽으면 `last_run_date`가 그대로
  남아 다음 실행이 재시도할 수 있어야 한다. 상세는 [[투자_포트폴리오_원장]] "반쯤 갱신" 항목.
- **커밋 권한은 Actions 기본 `GITHUB_TOKEN`으로 충분하다.** 워크플로에 `permissions: contents: write`만
  주면 되고, PAT를 따로 발급해 시크릿에 넣을 필요가 없다.
- **처음엔 `workflow_dispatch`(수동 버튼)로만 돌린다.** 커밋·푸시까지 정상인지 눈으로 여러 번
  확인한 뒤 마지막에 `schedule`을 켠다.
- **의존성은 `requirements.txt` 전체가 아니라 매매용만 설치한다.** 매매 스크립트는 streamlit·
  jupyterlab·matplotlib가 필요 없는데, 전체를 설치하면 매일 수 분씩 낭비된다(jupyterlab이 특히
  무겁다). 별도 `requirements-trading.txt`를 둔다. **V1은 규칙 기반이라 신규 패키지가 아예
  없다** — `anthropic`·`pydantic`은 0단계에서 설치 확인만 해뒀고 지금은 안 쓴다(LLM 전환 시 재사용).
- **원장을 실제로 갱신하는 실행은 Actions 한 곳으로 일원화한다.** 로컬 실행은 디버깅용이며
  `data/portfolio/`를 건드리지 않는 dry-run 옵션을 둔다 — 안 그러면 로컬과 원격 이력이 갈라진다.
